# ADR-002: Offline-First SQLite + Supabase Sync & Monotonic Conflict Resolution

## Status
Accepted

## Context
PRD Section 13 mandates:
- Supabase (PostgreSQL, Auth, Row Level Security) as the primary cloud database.
- Expo SQLite for offline-first local persistence of content, progress, vocabulary, review schedules, and pending changes.
- A deterministic synchronization strategy that never silently overwrites newer user progress.
- Full testability across Node/Jest environments as well as iOS and Android devices via Expo.

## Decision
1. **Normalized SQL Migrations:** Maintain explicit versioned SQL migrations under `supabase/migrations/` covering all entities, foreign keys, indexes, and RLS policies.
2. **Driver-Adaptive SQLite Layer:** Implement `DatabaseService` using formal SQLite DDL schemas (`SQLITE_MIGRATIONS`) backed by `expo-sqlite` in native runtime and an isomorphic in-memory fallback when running under Node/Jest or environments without native SQLite bindings.
3. **Transport-Injectable Supabase Layer:** Implement `SupabaseService` wrapping `@supabase/supabase-js`, configured via `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY`, safely operating in offline-guest mode when credentials are absent.
4. **Monotonic Merge Conflict Resolution:** In `SyncEngine`, merge `UserProgress` sets (`completedLessonIds`, `savedWordIds`) via set union and take `Math.max()` on cumulative counters (`totalLearningMinutes`, `bestStreak`), while selecting the latest timestamp on scalar preferences and FSRS card states.

## Consequences
- Learners can study completely offline without friction and synchronize safely when connected.
- All sync conflict edge cases and schema migrations are unit-tested without requiring live cloud credentials in CI.
- Ready for one-command Supabase deployment (`supabase db push`) and EAS native builds.
